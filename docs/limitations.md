# 已知边界与用例准入

本文有两个用途：

1. **告诉你能测什么**——有些失败是平台能力不足，不是你测的东西有问题；
2. **给准入检查提供依据**——`src/browser/admission.ts` 实现的判定规则来自这里。

---

## 为什么这份清单很重要

**假阳性是测试套件最致命的输出。**

如果一个用例踩中了本平台的已知边界，它会失败——但失败原因是**平台测不了**，
不是被测系统有缺陷。把这种失败和真实缺陷混在一份报告里，
整个套件的可信度就没了：人开始怀疑每一条红灯。

所以边界必须写在明处，且**在运行之前**就给出结论。
这正是准入检查（`admission.ts`）存在的理由——它不运行用例、不调用模型，
只做一次只读的页面探测，然后告诉你：

- **blocking**：这个用例不该跑；
- **warning**：跑得动，但结果要打折扣，原因如下。

---

## 不支持的能力

### 1. Shadow DOM

**状态：不支持（P1 计划）**

`snapshot.js` 只遍历主文档的 `document.querySelectorAll`，不递归
`element.shadowRoot`。因此 Web Components 内部的控件**根本不会进入元素表**，
agent 看不见它们。

P1 计划加约 10 行递归支持。届时需要考虑：

- 递归深度上限（嵌套 shadow root 可能很深）；
- 与 `identity()` 的配合——WeakMap 对 shadow 内的节点一样有效；
- 闭合模式（`mode: "closed"`）的 shadow root **永远拿不到**，这是规范的硬限制。

### 2. 跨域 iframe

**状态：不支持（P1 计划用 `f1:e7` 形式支持同源）**

跨域 iframe 内的 DOM 受同源策略保护，`page.evaluate` 在主文档上下文里读不到。
目前只覆盖主文档。

需要区分两种情况：

- **同源 iframe**：技术上可读，但目前没实现遍历。`admission.ts` 会报告
  `frames > 1` 作为 warning。
- **跨域 iframe**：`page.frames()` 能**准确枚举**（这是 Playwright 比纯 JS 探测强的地方），
  但内部控件读不到。若 goal 需要与其中的控件交互，直接判 blocking。

### 3. Canvas / WebGL 应用

**状态：不支持**

元素表来自 DOM，canvas 内部没有任何 DOM 节点。
如果整个应用渲染在 canvas 上，元素表会是空的。

`admission.ts` 检测到 `canvases > 0` 时给 warning；
若同时元素表为空，则判 blocking。

### 4. 文件上传

**状态：不支持，且被内置护栏主动拦截**

`snapshot.js` 把 `input[type=file]` 归入 `safe` 黑名单，不会进入元素表。
`guard.ts` 的内置护栏也会拦。

即使将来支持，也需要考虑「上传什么文件」这个用例层面的配置问题。

### 5. 新标签页 / 弹窗

**状态：不支持**

`target="_blank"` 打开的页面在**另一个** page 对象里。
当前 runner 只跟一个 page，不会自动切过去。

结果是：点了这样的链接之后，agent 会停在原页面，然后困惑于"什么都没变"，
最后判 `blocked`。这是**典型的假阳性来源**——看起来像站点坏了，
实际是平台没跟上。

### 6. 嵌套滚动容器

**状态：不支持**

`snapshot.js` 只处理**文档级**滚动：`scrollY` / `documentElement.scrollHeight`，
滚轮事件也发在固定坐标 `(550, 650)`。

如果目标内容在一个 `overflow: auto` 的内部容器里，滚动文档是滚不到它的。
`admission.ts` 检测 `nestedScrollContainers > 0` 给 warning。

### 7. 复杂键盘交互

**状态：部分支持**

支持的是：`ControlOrMeta+a` 全选后插入文本（用于替换输入框内容）。

不支持：快捷键组合、方向键导航（如自定义下拉用上下键选择）、
输入法候选、拖拽、右键菜单、`contenteditable` 的富文本编辑。

### 8. 可访问名解析不完整

**状态：已知不完全**

`snapshot.js` 的 `name()` 函数实现的是一个**简化版**的可访问名算法：
它处理 `aria-labelledby`、`aria-label`、`<label>`、`alt`、文本子节点、
`title`、`placeholder`。

它**不是**浏览器的完整算法。会漏掉的典型情况：

- `aria-describedby` 提供的补充说明；
- CSS `::before` / `::after` 生成的内容；
- 复杂表格的关联表头；
- `<fieldset><legend>` 的上下文。

**后果**：某些元素的可访问名可能为空或不准，导致 `label` 变成 role 兜底值，
断言与护栏的 label 匹配都可能失准。

**对应策略**：平台内建了「找不到控件通常是可访问名太差」这个信号，
可以当作可访问性健康度的副产品来看。但如果一个控件连人都难以命名，
不要指望 agent 能找到它。

### 9. 其他

| 能力 | 状态 |
| --- | --- |
| 后端副作用校验（查库 / 调 API 确认操作生效） | 不支持。**断言只覆盖前端可见状态** |
| 测试数据准备与清理 | 不支持 |
| 跨用例数据传递 | 不支持 |
| 参数化用例 | 不支持 |
| 登录态管理 | 底层 `storageState` 能力已规划，但无界面与用例字段 |
| 多角色流程 | 不支持 |
| 视觉回归（像素比对） | 不支持，且不在计划内 |

## 用例准入清单

**本表是准入判定的权威来源。** `src/browser/admission.ts` 的规则必须以此为准，
改本表就要同步改它，反之亦然。

> 这两处目前靠人工同步——**本身就是一处待消灭的双事实来源**，正是 D5 想避免的东西。
> 建议把规则写成数据（`ADMISSION_RULES`，每条含 `id` / 判定 / 文案），文档从它生成。
> 见 [architecture.md §11.2](architecture.md)。

写新用例前逐条过一遍。任一条命中「blocking」就不该写成 jevtest 用例。

| 检查 | 结论 |
| --- | --- |
| 目标控件在 shadow DOM 里？ | 🚫 blocking（P1 后重估） |
| 目标控件在跨域 iframe 里？ | 🚫 blocking |
| 页面是 canvas / WebGL 渲染的？ | 🚫 blocking |
| 需要上传文件？ | 🚫 blocking |
| 需要打开新标签页并继续操作？ | 🚫 blocking |
| 目标内容在内部滚动容器里？ | ⚠️ warning，多半会卡住 |
| 需要键盘快捷键 / 方向键 / 拖拽？ | ⚠️ warning |
| 需要精确的字段级校验或边界值？ | ⚠️ 改用 Playwright |
| 需要验证后端状态真的变了？ | ⚠️ 本平台只能看前端 |
| 需要每次都跑（每次 commit）？ | ⚠️ 成本不允许，考虑定期跑 |
| 需要确定性复现路径？ | ⚠️ agent 路径不保证一致 |
| 控件可访问名很差或为空？ | ⚠️ agent 可能找不到。考虑先修可访问性 |

## 这些边界之外，仍然存在的风险

即使用例没踩中上面的任何一条，仍有两类风险：

### 1. 有效的动作不等于正确的动作

模型可以从候选集里挑一个语法上完全合法、但业务上错误的目标。
平台能保证「它没越界」，不能保证「它选对了」。

这正是断言层存在的理由——**永远不要只看 `status: done`**。
参考项目的原话是 `A DONE choice is not proof of success.`

### 2. 站点改版

断言建立在可访问名与可见文本上，因此比选择器抗改版得多，但**不是免疫**：
文案一改，`labelContains` 就失配。

所以断言尽量用**语义稳定**的部分（角色、结构性的文案），
避免依赖营销文案（它们改得最勤）。
