# 选型记录

每个决定记三件事：选了什么、为什么、**放弃了什么**。
第三条最重要——没有记录被否决的方案，后来者会重新提一遍同样的问题。

---

## D1. 用 TypeScript / Node 而不是 Python

**决定**：Node 22 + TypeScript（ESM）。

**为什么**：

1. **最难的部分零成本复用。** 参考项目里最精巧的代码是 `snapshot.js`
   （107 行原子 DOM 快照 + WeakNode 身份 + 语义守卫），它本身就是 JavaScript。
   用 Python 意味着要把这段逻辑重写一遍，而它是最容易写错的地方。
2. **没有 sync/async 分裂问题。** Playwright 在 Node 里是原生异步的。
   Python 版的同步 API 使用 greenlet，不能直接用在 asyncio 事件循环里，
   而 Web 服务天然是异步的——这会逼出一个别扭的线程池方案。
3. **白送最强调试工具。** `context.tracing.start()` 产出 `trace.zip`，
   `npx playwright show-trace` 直接打开，带时间轴与每步 DOM 快照。
   Python 版也有，但 Node 版是参考实现，生态更完整。
4. **schema 与类型同源。** 用 zod 定义一份 schema，同时得到运行时校验与 TS 类型，
   用例、报告、API 的契约不会在「校验」与「类型」之间漂移。

**放弃了什么**：Python 生态里 `pytest` 的成熟度、以及和上游仓库语言一致带来的
移植便利（改为逐行对照重写）。

**什么情况下该反悔**：如果团队完全不会 JS/TS，维护成本会盖过上述收益。

---

## D2. 用 `playwright` 库而不是 `@playwright/test` 的 runner

**决定**：只用 `playwright` 这个 npm 包，不用 `@playwright/test`。

**为什么**：

`@playwright/test` 提供了大量本项目的刚需——test runner、worker 并行、
重试、HTML 报告、JUnit 导出、trace viewer、fixtures。放弃它看起来是浪费。

但它的前提是**用例即代码**：一个用例就是一个 `.spec.ts` 文件。
而本项目的核心需求恰恰相反——**用例由 Web 表单驱动，运行时要动态生成**。
把 YAML 编译成临时 spec 文件再交给它跑，会带来一串新问题：
进程生命周期、报告回读、进度推送、用例与运行的对应关系。

我们需要自研 runner（job queue、实时进度、预算刹车、用例版本快照），
这已经超出了 `@playwright/test` 的设计意图。

**但 trace viewer 没放弃。** 用底层的 `context.tracing.start/stop` 自己产出
`trace.zip`，格式完全一致，官方的 `show-trace` 照常能用。
这是这个决定里最划算的一部分：**白拿最重要的那个工具，不接管运行模型。**

**放弃了什么**：现成的 HTML 报告与 JUnit 导出（自己写，约 200 行）、
`@playwright/test` 的 fixtures 体系、它的 `expect` 断言库。

**什么情况下该反悔**：如果用例最终变成「技术同学写代码」而非「表单填写」，
`@playwright/test` 会明显更省事。

---

## D3. 用 `node:http` 而不是 Hono / Express / Fastify

**决定**：Node 内置 `node:http` + 自写约 40 行路由。

**为什么**：

1. **依赖数量。** 本项目运行时依赖刻意控制在 3 个
   （playwright / zod / yaml）。加一个 Web 框架就是 +2。
2. **Hono 的 `writeSSE` 有已知问题**——连接静默断开时可能挂起且
   `onAbort` 不触发（[#1902](https://github.com/honojs/hono/issues/1902)、
   [#3540](https://github.com/honojs/hono/issues/3540)）。
3. **我们本来就不需要 SSE**（见 D4），而 SSE 正是 Hono 相对标准库最大的优势。

**放弃了什么**：成熟的路由、中间件、body 解析、类型化上下文。
实际要手写的是：路径模式匹配（十几行）、请求体流式限长（十几行）、
静态文件服务（十几行）。总量可控。

**什么情况下该反悔**：端点数量增长到几十个、或需要 SSE/WebSocket。
反悔成本低——路由集中在 `web/api.ts`，换框架只改两个文件。

---

## D4. 进度用轮询而不是 SSE

**决定**：前端 500ms 轮询 `GET /api/runs/:id/events?since=<seq>`。

**为什么**：

- 进度事件是**服务端单向**推送，SSE 的双向能力用不上；
- 一次运行约 10~20 步，几步每秒，500ms 轮询完全够用；
- SSE 会引入连接生命周期、心跳保活、断线重连、代理缓冲等一串失败面；
- 事件模型本身是 SSE 兼容的（`seq` 天然对应 `Last-Event-ID`），
  真要换，改动集中在一个端点和 `web/events.ts`。

**放弃了什么**：更低的延迟与更少的请求数。在本项目的规模下不值得。

**什么情况下该反悔**：如果实测发现长运行（>5 分钟）时轮询体验差，
或者步数密度远超预期。

---

## D5. 用例格式用 YAML，Web 表单是它的图形编辑器

**决定**：`case.yaml` 落盘为**唯一事实来源**；表单只是编辑它的界面。

**为什么**：

两套模型（表单一套、文件一套）迟早会漂移——表单里能设的字段文件里没有，
或者反过来。漂移之后没人知道哪边是真的。

单一事实来源解决了这个问题，并带来两个额外好处：
**用例可以进 Git**（有 diff、有 review、能回滚），
**非技术同学也能用表单编辑同一份文件**。

保证不漂移的机制：`tests/yaml-roundtrip.test.ts` 锁「YAML ↔ 对象」逐字节往返，
`tests/frontend.test.ts` 锁「对象 → 表单草稿 → 对象」语义不变。

**放弃了什么**：纯数据库存储的灵活性（查询、并发编辑、权限）。
本项目是单机工具，文件足够。

**什么情况下该反悔**：如果变成多人协作的集中式平台。

## D6. 断言分三层

**决定**：`final`（最终页面）/ `trajectory`（动作轨迹）/ `quality`（质量与成本）。

**为什么**：

上游只有一个**硬编码给 Google Flights** 的 `verify()`。要泛化它，
先得想清楚断言到底在回答哪些不同的问题——它们混在一起会给出误导性的报告。

| 层 | 回答的问题 | 失败的典型含义 |
| --- | --- | --- |
| `final` | 最终页面对不对？ | 功能有缺陷，或断言写太严 |
| `trajectory` | 过程走对了吗？碰了不该碰的吗？ | 它绕路了，或护栏失效 |
| `quality` | 跑得稳不稳、贵不贵？ | 用例不稳，或性能回归 |

分开的实用价值：一次失败时能立刻定位到**是哪一类问题**。
「页面是对的但它绕了 40 步」和「页面根本不对」需要完全不同的处理。

**放弃了什么**：一层 `assert` 列表的简洁性。

---

## D7. `trajectory` 断言按 label 而非内部 id

**决定**：轨迹断言用 `labelContains` / `role` / `kind` 匹配，
不用内部的 `e7` 这种 id。

**为什么**：内部的 `choice` 是 code-owned 节点身份，**只在单次观测内有效**。
节点被替换会拿到新身份，导航会重置整个缓存。
因此它**跨运行完全不可比**——用 `mustUse: ["e7"]` 断言毫无意义。

而轨迹记录里存了人类可读的动作标签（上游 `agent.py:121-141`），
它才是稳定的、有语义的匹配依据。

**放弃了什么**：精确匹配某一次特定点击的能力。
但那个能力本身就是幻觉——下一次运行它就不是那个 id 了。

---

## D8. `status` 与 `passed` 是两个类型，且都保留

**决定**：`status: RunStatus`（循环如何结束）与 `passed: boolean | null`
（断言判决）相互独立。

**为什么**：上游 README 里有一句核心信条——
**A `DONE` choice is not proof of success.** 它用独立的 `verify()` 检验结果，
而不是相信模型的自我判断。

把这条纪律固化到类型层面，写错编译器就会拦下。同时 `passed` 允许为 `null`，
表示「未能求值」（例如第一步之前就超预算了，没有最终页面可断言）——
把它当成 `false` 是另一种谎报。

**放弃了什么**：一个布尔字段的简洁性。

---

## D9. 结果有三种状态：passed / failed / skipped

**决定**：`CheckResult` 带 `skipped` 字段，而不是布尔值。

**为什么**：

TypeSafe 给出真实的概率分布，但通用 LLM 通常只回一个选择，
合成出来是 one-hot 1.0。此时 `quality.minTargetProbability: 0.3`
**永远通过**——因为「被选中项的概率」恒等于 1.0。

这是一个**假通过**，比失败更危险：它让人以为测过了，而实际没有覆盖。

所以引擎通过 `capabilities.probabilities` 声明自己给的是
`full` 还是 `degenerate` 分布；断言层看到 `degenerate` 时，
概率类检查返回 `skipped`，报告显示「跳过」。

**放弃了什么**：一个布尔字段的简洁性（同上）。

**推论**：报告里「跳过」的视觉呈现必须与「通过」明显不同。

---

## D10. 只读模式在动作空间构造阶段实现

**决定**：`mode: readonly` 时，变更型操作在 `buildActionSpace` 里就被剔除，
不进入候选集。而不是「模型选了之后我们拒绝」。

**为什么**：

| | 构造阶段剔除 | 事后过滤 |
| --- | --- | --- |
| 模型能否选中 | **物理上不能** | 能选中，被拒绝 |
| 拒绝逻辑写漏的风险 | 不存在 | 每加一个操作都要记得加判断 |
| 报告能说什么 | 「本运行不可能发生变更」 | 「我们相信它没发生」 |

这复用了上游最有价值的机制：**有限选择空间即安全边界**。
上游的模型从来只能从观测到的元素里挑一个索引，
这个约束本身就消灭了一整类风险（伪造选择器、注入脚本、越界点击）。
只读模式是同一思路的延伸。

`core/guard.ts` 的 `auditTrajectory` 仍会事后核对一遍——
**「物理上不可能」和「报告需要证据」是两回事。**

**放弃了什么**：没有。这个实现方式严格优于事后过滤。

---

## D11. 每个用例一个 `BrowserContext`，删掉全局锁

**决定**：一个 Chromium，每用例一个 context；不做全局串行化。

**为什么**：

上游用一把全局 `LOCK` 序列化所有浏览器步进
（`demo.py:111-112`），因为所有标签页共享用户已有的 Chrome profile。

换到 Playwright 后：

| | 上游 | 本项目 |
| --- | --- | --- |
| profile | 共享 | 每 context 独立 |
| cookie/localStorage | 互相污染 | 隔离 |
| 并行 | 不可能 | 天然支持 |
| 登录态 | 手动维护 | `storageState` 复用 |
| 单实例成本 | 新建标签页 | ~50ms、80~150MB |

**锁必须删掉**——它存在只是因为当时只有一个共享标签页，
在隔离是天然的情况下，锁只会杀掉并发。

**放弃了什么**：复用用户 Chrome 已有的登录态（改为 `storageState` 机制），
以及直接观察用户浏览器窗口的便利（调试时略麻烦，靠 trace viewer 补）。

**代价**：Playwright 自带的 Chromium 不是真实 Chrome，且带
`--enable-automation` 特征。内部 staging 无所谓，测三方站点时要留意。

## D12. 引擎可插拔，校验在引擎之外

**决定**：定义供应商无关的 `DecisionRequest` / `DecisionResult` IR；
`validateChoice` 住在 `core/policy.ts` 而不是引擎里。

**为什么**：

绑死 TypeSafe 会让项目受制于单一供应商的可用性与定价。
但「可插拔」很容易做成表面功夫——如果每个引擎各自校验自己的输出，
换一个引擎就等于换一套安全保证。

把校验放在 `core/` 意味着：**引擎无法产出越界的选择**。
即使某个实现有 bug 返回了不存在的 id，也会被挡在执行之前。

同时 `capabilities` 让引擎如实声明自己的能力（是否支持文本生成、
概率分布是 full 还是 degenerate），断言层据此决定哪些检查可求值。

**放弃了什么**：引擎可以自由优化输出格式的便利（必须装进 IR）。

**代价**：IR 是为了同时容纳「TypeSafe 的多问题结构化输出」和
「通用 LLM 的 tool use」设计的，对两者都不是最优解。

---

## D13. 报告自包含（内嵌用例快照与 digest）

**决定**：`runs/<runId>/` 里存一份产生本次运行的 `case.yaml` 快照，
报告里记录 `caseRevision` 与 `caseDigest`。

**为什么**：

用例会被修改。如果报告只记录 `caseId`，一周后翻出一份失败报告，
你不知道当时跑的是哪个版本的用例——那个失败可能已经被修好了，
也可能被你的修改掩盖了。

自包含之后，任何一份报告都能精确回到产生它的用例版本。

这是上游 `measurement.json` 里 `source_hashes` 的正规化版本——
它记录了源码的 hash，本项目把同样的思路用在用例上。

**放弃了什么**：磁盘占用（每个 run 多一份 YAML，微不足道）。

---

## D14. 内置护栏只增不减

**决定**：用例只能往护栏里**追加**规则；移除内置规则需要显式设置
`allowDefaultOverride: true`，且报告应打红色横幅（**尚未落地**：报告目前不记录这件事，见 [limitations.md §9](limitations.md)）。

**为什么**：

安全网最常见的失效方式不是「没配」，而是「被悄悄关掉」——
某次调试时注释掉一行，然后忘了加回来。

让它**默认安全，放弃安全需要明说并留痕**，比相信人的自觉可靠。

**放弃了什么**：纯粹配置的灵活性。这个交换是值得的。

---

## D15. 用 `node:test` 而不是 vitest

**决定**：Node 内置测试运行器。

**为什么**：`node:test` 在 Node 22 上已经足够（支持并发、子测试、mock、
快照）。引入 vitest 意味着 +1 个开发依赖和一整棵依赖树，
而本项目需要的能力它并不比内置的多。

**放弃了什么**：更丰富的断言 API、更好的 watch 模式、更成熟的生态集成
（如浏览器模式的测试）。

**什么情况下该反悔**：如果需要组件测试或更复杂的 mock 场景。

---

## D16. CLI 走进程内调用，不经过自己的 HTTP 服务

**决定**：`jevtest run` / `validate` / `import` 直接调用模块（`cli.ts` 的 `createWiring`），
`doctor` 调 `web/api.ts` 的 `handle()` 但**不经网络**。

**为什么**：为了跑一个用例去绑端口、生成一次性令牌、启动一个「浏览器都还没起」的 HTTP 服务、
再让它把请求转发一次，只增加失败面；CI 里并行跑多个 jevtest 还会撞端口（或需要各自分配端口）。
而 `doctor` 要检查的是配置与依赖，不是 TCP——它走的是**同一个 handler**，只是不经过 socket。

**放弃了什么**：「CLI 就是 HTTP API 的一个客户端」这种整齐。前端与 CLI 在
**语义与业务逻辑上**共用同一套（同一份路由与模块），在传输层不共用。

**什么情况下该反悔**：若要支持「CLI 连远程 jevtest 服务」（多机场景），就必须真的走 HTTP——
那时 `createWiring` 与一个纯 HTTP 客户端会是两条并列的通路，而不是二选一。

---

## D17. 只读模式剔除的角色从 6 个扩到 10 个

**决定**：`READONLY_BLOCKED_CLICK_ROLES` 增加 `menuitemradio`、`menuitemcheckbox`、`option`、`gridcell`。

**为什么**：最初那 6 个（`docs/case-format.md` §mode 里的原始清单）是照搬参考项目的概念定的，
漏了 ARIA 的选项与菜单选项，以及日历/表格的单元格。它们的点击**同样会改变被提交的值**，
与勾选框同类。少列一个，只读用例就能悄悄改掉页面状态——而报告里那句
「本运行不可能发生变更」就变成了假话。

**放弃了什么**：只读用例能点到的控件变得更少（例如点不开日历选择日期）。这是刻意的取舍：
只读的承诺要么是真的，要么就别写。

**代价与防漂移**：清单现在同时写在代码与两份文档里，因此加了一条测试，
从**代码常量**出发逐条验证、并比对文档里的清单——两处事实来源靠测试钉住，靠人同步必然漂移。

---

## D18. 前端引入 Bootstrap，经 `/vendor/*` 静态提供

**决定**：`bootstrap`（`^5.3.8`）进 `dependencies`，前端从 `/vendor/bootstrap/dist/css/*.min.css`
引它的样式表。`VENDOR_EXTENSIONS` 因此从 `.js` / `.map` / `.json` 扩到含 `.css`。

**为什么**：

前端原先是一份手写 CSS（约 60 行），后来要支撑的界面（用例列表、表单编辑器、
运行结果页、断言逐条明细、事件流）已经不是「加几十行」的规模。手写下去的真实代价
不是行数，而是**一致性**：间距、层级、focus 态、深浅色各自为政，每加一个视图都要
重新决定一遍。Bootstrap 把这些决定收敛成一套既有约定。

经 `/vendor/*` 而非 CDN：这个服务只监听回环、且刻意不依赖外网
（`docs/architecture.md` §8），从 CDN 引样式会让「离线可用」这条作废。

**放弃了什么**：

- 「运行时依赖只有 3 个」这条硬约束（现在 4 个）。它是**可以被放弃的**——那 3 个是
  出于「每个依赖都是一处长期维护面」的判断，而不是数字本身有魔力。
- 前端的完全自主样式（继承 Bootstrap 的设计语言，包括它的间距刻度与栅格）。

**代价**：

- `/vendor/*` 从「只为 zod 存在」变成「前端资产通道」。它是全项目**唯一**的动态文件
  服务路径，也就是唯一的目录穿越风险点——放行 `.css` 不引入新的风险面
  （静态读取，扩展名只决定「能不能读」，不存在按内容执行的路径，且 `.css` 不像
  `.html` 那样会被注入令牌），但这条路由的总风险随它服务的东西变多而变多
  （见 `docs/security.md` §5）。
- 前端不再零依赖构建之外的约束——但只要不引入打包器，这条底线还在。

**什么情况下该反悔**：若前端开始需要 JS 组件（`bootstrap.js` 的 dropdown/modal 之类），
就该重新权衡——那会把 `/vendor` 从「读几个静态文件」变成「运行第三方脚本」，
与 `docs/security.md` 的信任边界直接相关。届时更稳的做法是把需要的 CSS/JS
**vendor 进仓库**（进 `src/web/public/`），而不是让 `/vendor` 指向 `node_modules`。

## D19. 界面按「此刻要判断什么」分档，编辑器以草稿为唯一事实来源

**决定**：三条一起。

1. **编辑用例**分成四档（基本 / 断言 / 预算与护栏 / 保存内容）。
2. **断言不再按 schema 的三层平铺**，改成**配方行**——一行一句人话
   （「最终页面包含文本」「结束方式必须是」……），每行落到 schema 的一处。
   配方覆盖不到的构造不在界面上消失，而是收进同一档的「其他（配方之外的断言字段）」，
   非空时默认展开。
3. **结果页**判决卡常驻，下面按 断言 / 轨迹 / 事件日志 分档；运行中默认落在
   事件日志，结束后默认落在断言（用户自己点过之后就不再替他切）。

配套的三条实现约定：标签页与折叠**手写 / 用原生 `<details>`**（不引 `bootstrap.js`，
理由见 D18）；**编辑器的草稿是唯一事实来源**，`formToDefinition(draft)` 是纯函数，
控件一律在 input 时写回草稿；构建子节点列表统一用 `setChildren(node, [...])`。

**为什么**：原先的编辑器把 schema 平铺成一页，既难用、手动配置也太繁琐。当时一页 38 个控件，**其中 13 个
只有 placeholder 没有 label**——填进第一个字符之后就再也看不出那一格是什么；
断言三层里的 12 个 text-match 输入框还都是 `<input>`，而 HTML 规范规定
`<input>` 的值里不能有换行，于是「每行一条」这句 placeholder 是在承诺一件
输入框做不到的事。schema 里约 53 个叶子槽位一个都不能少，所以出路不是删字段，
是分层：**默认只露出常用路径，其余可发现但不挡路**。

字段与交互的映射按「用户此刻要做的判断」排，而不是按 schema 的结构排。
配方那句话直接取自 `docs/writing-cases.md §3`——界面与文档用同一套词汇。

**放弃了什么**：

- **一页看到所有字段。** 要改 `minTargetProbability` 得先切到断言档、
  再展开「其他」。这是刻意的：那些字段不常用，而常用路径值得一条干净的路。
- **第 4 档显示 JSON 而不是 YAML。** 真正的规范化 YAML 只有服务端
  `schema/yaml.ts` 会写；前端自己实现一份必然与它漂移，那就是在界面上撒谎。
  要看真 YAML，用同档的「导出已保存的 YAML」（走 `GET /api/cases/:id/export`）。
- **标签页与折叠没有过渡动画**（Bootstrap 的 collapse/tab 才有）。手写的四十行
  换掉一次 `/vendor` 信任边界的重估，值。

**代价与防漂移**：`tabs()` / `setChildren()` / `RECIPES` / `RAW_FIELDS` 几张表让前端代码明显变长。
真正的风险是**配方这层视图会不会把用例改坏**——载入一个用例、界面重画一遍、再保存，
中间丢一条断言是不会报错的。所以 `tests/frontend.test.ts` 直接 import `lib/core.js`
（D22 之前是把 `app.js` 里标了 `#region 纯函数` 的两段抠出来 `new Function`），跑三件事：
种子用例往返语义不变、**每个配方与每一处原始字段都落得下去**、以及空 `statusIn` 原样活着。
往 `lib/core.js` 里加代码时不许引用 DOM——那是这个项目里唯一能不引 DOM 测试环境就测到前端逻辑的口子。

> D22 修订了本条的界面部分：编辑器从四个标签页改成单页三节 + 节目录，「保存内容」改成抽屉；
> 结果页不再分档，改成判决带 → 失败摘要 → 轨迹 → 断言 → 原始事件。草稿与配方的约定不变。

**什么情况下该反悔**：若配方这层视图开始需要「一条断言里混合配方内外的字段」，
说明它已经从视图变成了数据模型，那时该重新设计的是数据形状而不是加特例；
若要给界面加 modal / tooltip 之类的 JS 组件，先按 D18 重估 `/vendor`。

## D20. BLOCKED 要过半才结束运行；打开起始页先等网络安静

**决定**：
- 模型选了 BLOCKED、但它的概率不到 `BLOCKED_MIN_PROBABILITY`（0.5）时，**不结束运行**，
  改走概率最大的非终止操作（目标取该操作 target head 自己的选择），并发一条 `run.log` 说明。
  一次运行最多这样替换 `MAX_WEAK_BLOCKED_OVERRIDES`（3）次，之后照常接受 BLOCKED。
  DONE 不受影响；分布是合成的（degenerate）时也不替换。
  （D25 起 DONE 也要过半，常量改名为 `TERMINAL_MIN_PROBABILITY` / `MAX_WEAK_TERMINAL_OVERRIDES`，次数两者合计。）
- `goto` 之后先等 `networkidle`，最多 `LOAD_SETTLE_TIMEOUT_MS`（5s），再做第一次观测。

**为什么**：一次真跑（后台管理页）里两件事叠在一起。第一次观测落在 DOMContentLoaded
时，列表和「批量导入」按钮还没从接口回来，模型看到的只有导航栏，于是选了 BLOCKED。
页面加载完之后又决策了两次，模型给 BLOCKED 0.46、CLICK 0.35、TYPE_TEXT 0.15。
超过一半的概率认为还能动，但 BLOCKED 是单项最大，运行就结束了。
BLOCKED 不可逆，而一步走错的代价只是一步：两者不该用同一条「取最大项」的规则。

**放弃了什么**：
- 「执行的永远是模型的 argmax」不再无条件成立。替换出来的那一步是在低把握下走的，
  报告里记录的是该操作自己的概率（例如 0.35），不会冒充成模型很确定。
- 起始页的第一次观测会晚到最多 5s：带轮询的页面永远等不到 networkidle，每次都会用满这 5s。
  只在 goto 上等，动作之后不等，否则这样的页面每一步都会慢 5s。

**什么情况下该反悔**：如果替换出来的步骤大多被护栏拦下，或者只是在原地空转，
说明模型在这些页面上的犹豫是对的，应该把阈值调低，或者改成「先 WAIT 再重判」。
如果换了一个会校准概率的引擎，这道闸可以去掉。

## D21. 被遮挡的元素观测时就不进候选集；连续丢弃 3 次决策判 blocked

**决定**：
- `snapshot.js` 收集候选时对每个元素的中心点做一次 `elementFromPoint`，没命中它自己（或它的后代）
  就不进候选集。标准与输入前的命中测试（`resolveTargetInPage`）完全相同。
- 自上一次成功执行以来，决策在执行前被丢弃（陈旧 / 目标不可用）连续达到
  `MAX_CONSECUTIVE_DISCARDS`（3）次，以 `blocked` 结束，原因里带上最近一次丢弃的理由。

**为什么**：一次真跑（采集导入设置弹窗）里，「图片设置」下的复选框被弹窗的滚动区裁掉，中心点落在底栏上。
它照样进了候选集，模型选中它，输入前的命中测试判 occluded，决策被丢弃、重新观测、再问模型。
丢弃的决策不产生 StepRecord，无进展检测看不到；请求里只有执行过的动作，模型也不知道上一次没点成。
页面没变，模型就给出同一个答案——同一个目标连问 16 次，占了整次运行 83% 的 input token，直到预算耗尽。
单次调用本身并不大（约 10k token），真正的浪费是这个没有上限的循环。

**放弃了什么**：
- `snapshot.js` 与上游多了一处差异（文件头有登记），将来 diff 上游时要记得这一行。
- 观测恰好落在短暂的遮罩（loading 层、toast）上时，被盖住的元素会暂时从候选集里消失，
  模型可能在这一步选 WAIT。这比选中一个点不到的目标便宜。
- 页面持续地、语义上地变化（守卫比较的容器文本一直在变）时，会被判 blocked 而不是一直重试。
  以前这种页面也跑不下去，只是会耗到预算上限才停。

**什么情况下该反悔**：如果出现大量「能点但被判遮挡」的误伤（例如某个组件库用透明层接管点击），
应当让两处命中测试一起放宽，而不是只放宽其中一处——两处标准一旦分叉，这条问题会原样回来。
如果引擎请求里能带上「上一次被丢弃的决策」，连续丢弃的上限可以放宽。

## D22. 前端拆成原生 ES modules；反馈只有四种；每次观测默认截一帧

**决定**：
- `app.js`（3400 行）拆成 `lib/`（api、纯函数、格式化、路由状态）、`ui/`（反馈与通用组件）、
  `components/`（登录态流程、轨迹查看器）、`views/`（每个路由一张视图）。仍然不打包：
  浏览器直接加载 ES modules，`server.ts` 的静态路由本来就允许子目录。
- 所有失败只走四条路（`ui/feedback.js`）：**字段错误**挂在字段下方并在表单顶部汇总（字段名译成人话，
  可点击跳转）；**页面错误槽**一个视图一个、新的替换旧的；**toast** 报行内快捷操作的结果；
  **全局横幅**只报令牌失效与服务不可达。异步按钮一律走 `busy()`（执行期间禁用），
  确认一律走 `<dialog>`，不用原生 `alert` / `confirm`（`frontend.test.ts` 静态检查）。
- 编辑器改成单页三节；结果页改成判决带 + 失败摘要 + 轨迹查看器（步骤时间线 + 所选那一步的截图与细节，
  运行中按事件实时拼出来）+ 按层分组的断言。
- `JEVTEST_RECORD_FRAMES` 默认开启：每次观测后截一帧，`StepRecord.frame` 是操作前画面，
  结束时那一页记在报告新增的 `finalFrame`。
- zod 的内置校验文案切到中文（`z.config(z.locales.zhCN())`，在 `schema/case.ts`）。

**为什么**：用户原话是界面、报错、交互「用起来非常不舒服」。具体是：错误落在九个不同的地方，
有的越堆越多、有的完全静默；校验错误直接列 `assertions.final.controls.2.valueEquals` 这种路径和英文；
保存能双击出假冲突，原始行改了不标脏，刷新就丢稿；结果页不能取消、重跑、跳回编辑；
轨迹的「画面」一列恒为空——截图通路从来没有接上。单文件 3400 行则让这些问题很难被一次看全。

**放弃了什么**：
- 模块之间的 import 让前端的文件数从 1 变成十几个；`frontend.test.ts` 改为扫描全部模块。
- 截图默认开启让每步多几十毫秒（计入墙钟预算），每帧约 100~150 KB 磁盘。
- 编辑器不再有标签页的「只露常用字段」：三节都在一页上，靠节目录与折叠控制密度。

**什么情况下该反悔**：模块数多到需要依赖图才能看懂、或者要用 npm 上的前端库时，
那时引入构建工具（Vite）比手写更划算；大批量跑、只关心通过与否时用 `JEVTEST_RECORD_FRAMES=off`。

## D23. 页面提示单独交给模型；点了没反应的目标暂时移出候选

**决定**：
- `snapshot.js` 额外返回 `notices`：当前可见的页面提示。收两类——`role=alert/status`、`aria-live`
  的语义提示，以及 id/class 像提示（toast / message / msg / notif / alert / snackbar）、自身
  fixed/absolute 定位、宽度不到视口 90% 的浮层。只收最外层、每条 ≤200 字、至多 5 条。
- 引擎请求里，当前页的提示置顶在 `page.text` 前面；每条近期动作的 `action` 串后面带上
  「这一步之后页面显示了什么」。报告的 `StepRecord.notices` 记同一份，界面在步骤上直接显示。
- 一次 CLICK 之后 `pageChanged` 严格为 `false`，该节点在页面变化之前不再作为 CLICK 候选
  （构造期剔除，输入 / 选择不受影响）；页面一变（`true`）或没能观测（`null`）就全部放回。

**为什么**：一次真跑（采集导入 eBay 产品库）里，导入表单默认「手动选择SKU」，点「确定」弹出
「请输入SKU」。这条 toast 在 `page.text` 中间，而 25 个输入框的占位符也叫「请输入SKU」，
模型分不出哪一条是报错。请求里明明有 `page_changed: false`，它还是把同一个「确定」连点了四次，
直到无进展闸判 blocked。出路（改选「自动以ListingID或ASIN为SKU」单选项）其实一直在候选集里。

**放弃了什么**：
- `snapshot.js` 与上游又多一处差异（文件头第 5 条）。
- 上游的 `state.page` 与 `recent_actions` 各有固定的键，多一个键服务端只回 `Invalid request.`，
  所以提示只能拼进已有的字符串字段，不能新开字段。
- 自造浮层靠命名与定位猜：class 不像提示的 toast 收不到；像提示的常驻浮层（例如带 message 的悬浮客服窗）
  会每步都出现在提示里。整宽横幅按常驻公告排除。
- 需要点两次才生效的控件（第一次只是聚焦、而页面指纹恰好不变）第二次点不到了。模型可以改点别的地方，
  或者等页面变化后再点。

**什么情况下该反悔**：如果提示里经常混进常驻浮层，应当改成只报「这一步之后新出现的」提示，
而不是继续加命名规则。如果剔除导致本来能走通的流程被判 blocked（例如双击才生效的控件），
就把剔除改成只在同一个目标连续两次没反应之后才生效。

## D24. 动作之后等页面安静再观测；无名勾选控件带上所在行；终止决策写进报告

**决定**：
- 每次 `act()` 输入之后，除了原来的两帧 settle，再等「页面安静」（`POST_ACTION_QUIET`）：
  动作之后才发出的 xhr / fetch / script 请求全部返回，且 DOM 连续 300ms 没有结构变化
  （节点增删、文本、class / hidden 等属性；不听 `style`）。上限 3s，等不到就按时继续。
  动作之前就在途的请求（长轮询）不算。
- `snapshot.js` 给没有可访问名的 checkbox / radio / switch 补上所在表格行：
  表头行记成 `checkbox · header row (usually select all) · <行文本>`，数据行记成
  `checkbox · row <n> · <行文本>`（行文本截到 80 字）。有名字的、不在行里的不变。guard 不变。
  （已被 D28 的通用规则取代。）
- 以 DONE / BLOCKED 结束时，报告新增 `terminalDecision`：步号、各操作的概率、置信、分布、
  所在页面与截图帧、用量。Markdown 报告与界面「结束」一项都显示它。

**为什么**：一次真跑（采集导入 eBay 产品库，两次运行轨迹完全一样）里三件事串在一起。
第一步，元素表里表头全选框和 50 个行复选框都叫 `checkbox`，目标写明「不要点表头全选框」，模型还是点了全选。
第三步，点「导入eBay产品库」之后只等了两帧就观测，弹窗外壳已出现、SKU 选项还在路上，
候选里只剩「确定」，模型就点了它，弹出「请输入SKU」。选完 SKU 方式之后，模型对着历史
（勾选、导入、确定、选方式都「做过了」）回了 DONE，运行判 `done`。而 DONE 不产生 StepRecord，
报告里查不到它当时给 DONE 多少概率，`decisions` 为什么比 `steps` 多两次也看不出来。

**放弃了什么**：
- 每个动作之后至少多等 300ms；动作引出长连接、或页面持续改 DOM 时，每步会等满 3s（计入墙钟预算）。
  D20 里「动作之后不等」的说法因此作废：那条防的是整页 `networkidle` 被无关的轮询拖住，
  这里只看这次动作引出的请求，所以不受那种页面影响。
- 点击处理器 300ms 之后才发出的请求、只靠 `style` 显隐的内容等不到。
- `snapshot.js` 与上游又多一处差异（文件头第 6 条）。行文本让 label 变长，
  按 `labelContains: checkbox` 写的轨迹断言照样匹配，按整串写的会变。
- `terminalDecision` 只记生效的那一次；新鲜度复查丢弃的终止决策仍然只有 `step.skipped` 事件。

**什么情况下该反悔**：如果大量页面每步都等满 3s（报告里 `observedMs` 相邻两步间隔接近 3s），
说明 DOM 静止这条太严，应当收窄监听的属性，或者只看网络。
如果 `terminalDecision` 显示提前的 DONE 大多概率不高，就给 DONE 也加一道和 BLOCKED 一样的过半门槛（D20）。

## D25. DONE 也要过半；页面提示不暗示因果；告诉模型视口外还有内容

**决定**：
- D20 的过半门槛推广到 DONE：DONE 不到 `TERMINAL_MIN_PROBABILITY`（0.5）时同样改走概率最大的非终止操作。
  替换次数 DONE 与 BLOCKED 合计至多 `MAX_WEAK_TERMINAL_OVERRIDES`（3）次，用完照常接受。
- 引擎请求里页面提示的措辞改成中性：置顶的标题注明「可能包含无关的后台通知」，
  近期动作后面写「之后可见、未必是这一步引起的」，不再写 `afterwards the page showed`。
- 请求 IR 新增 `state.scroll`（已滚过的高度、整页高度、视口高度）。typesafe 引擎在视口上方或下方
  还有 ≥40px 内容时，在正文前加一句「元素与正文只含视口；上方 / 下方还有约 N px（SCROLL_UP / SCROLL_DOWN）」。

**为什么**：D24 之后重跑同一个用例（采集导入 eBay 产品库），全选框与提前点「确定」都修好了，
但运行还是在「确定」没点时以 `done` 结束。`terminalDecision` 显示 DONE 0.41、CLICK 0.33、BLOCKED 0.18，置信 0.28。
诱因是选完 SKU 方式那一刻，右上角通知中心恰好弹出一条后台任务的「AI生成Listing: 成功5个，失败0个」
（`div.nc-toast`）。它被当成页面提示置顶，还挂在这一步后面写成「之后页面显示了」，
而目标写的是「出现导入完成的提示即为通过」。D20 当时认为「DONE 的对错由断言判」，
但断言只能事后判失败，拦不住运行提前结束。同一次运行里模型还只勾了 1 个产品（目标要 2 个）：
第 2 行在首屏之下，请求里没有任何「下面还有内容」的信息。

**放弃了什么**：
- 真的做完了、但模型只有四五成把握时，会多走至多 3 步才结束（同 D20 的 BLOCKED）。
- 措辞改中性只能减轻误导：通知中心的推送和业务提示都是浮层 toast，`snapshot.js` 仍然分不开。
- 页面锁住滚动（弹窗打开时 `body { overflow: hidden }`）时，位置信息仍会说「下面还有内容」，
  模型可能白滚一次；那一步 `pageChanged: false`，由无进展闸兜底。
  内容在嵌套滚动容器里时整页高度不反映它，这里照样看不出来（见 limitations 的嵌套滚动容器一节）。

**什么情况下该反悔**：如果替换出来的步骤大多紧接着又回 DONE，说明模型的犹豫是对的，
应当改成「替换一次后要求 DONE 的概率比上次更高才接受」，而不是继续加替换次数。
如果位置提示导致大量无谓的 SCROLL_DOWN（页面很长、目标就在首屏），就只在元素表为空或
目标明确提到「列表 / 前 N 个」时再提，或者把它放进 omittedActions 那类「看不见的东西」的统一说明里。

## D26. 同源 iframe 并进观测；读不到的跨域 iframe 要说出来

**决定**：
- `snapshot.js` 在每个同源 frame 里各跑一次（文件头第 7 条）。子 frame 里的候选几何换算到顶层视口，
  命中测试逐层做到顶层：每一层的父文档在该点命中的都必须正是那个 `<iframe>`。`resolveTargetInPage` 用同一条标准，
  返回顶层坐标，鼠标事件照常发在 page 上。
- 子 frame 的元素 id 写成 `f1:e7`，`node` 编码成 `frame 序号 * 1_000_000 + frame 内节点号`（`FRAME_NODE_STRIDE`），
  主文档的节点号不变。core 不知道 frame 的存在：policy 归并元素、agent 记「点了没反应」都照旧按 `node`。
  子 frame 节点的守卫连同那个 frame 的 timeOrigin / href 一起存，新鲜度检查、执行都在节点所在的 frame 里做。
- 正文在主文档之后按 frame 一段段接上，每段带 `[iframe f1: <标题>]`；滚轮落点所在的最里层 frame
  提供 SCROLL_DOWN / SCROLL_UP 与 `scroll`。
- 动作之后等待的请求类型加上 `document`，子 frame 的 DOM 也等安静。
- 视口里 ≥50x50 的跨域 iframe 计入 `Observation.unreadableFrames`：进请求 IR（引擎在正文前说明一句），
  首次出现或数目变多时记一条 warn，以 BLOCKED 结束时写进失败原因。
- 准入里「检测到 N 个同源 iframe，当前只遍历主文档」这条 warning 删掉。

**为什么**：一次真跑（`20260923-123817-ebay-57110e`，在刊登管理里创建 eBay 模板）点「+ 添加产品」后，
表单在弹窗里的同源 iframe 中，iframe 文档 1.7s 才回来。快照只读主文档，主文档又被弹窗遮罩盖住，
模型的输入从 8k–11k tokens 掉到约 1.5k，只剩弹窗外壳。滚了一次没反应，第 3 步回了 BLOCKED，
失败原因只有一句「模型选择 BLOCKED」。准入探测只在起始页做过一次，那时页面上还没有 iframe。

**放弃了什么**：
- 跨 frame 不是原子读取。代价由「每个动作只按它所在 frame 的守卫判新鲜、输入前逐层重做命中测试」兜住，
  但整页 marker 可能拼的是前后相隔几毫秒的两个 frame。
- 每次观测多出「每个同源 frame 一次 evaluate + 每个跨域 frame 三次往返」；广告、统计 iframe 多的页面会慢一些。
- 子 frame 正文接在主文档之后。弹窗盖住主文档时，主文档那段是噪音，预算吃紧时引擎从尾部裁，
  先被裁掉的反而是 iframe 那段。
- iframe 带 CSS `transform` 缩放或旋转时坐标会算偏；跨域 iframe 仍然完全不支持。
- 滚轮落点只按 frame 的矩形判断，不做遮挡检查；iframe 滚到底后滚轮串到父文档（scroll chaining）的情况也不算。

**什么情况下该反悔**：如果弹窗 iframe 的用例经常因为正文被裁而丢掉表单内容，就把「滚轮落点所在的 frame」
的正文排到最前面。如果跨域 iframe 的警告在真实页面上大多来自广告、客服挂件，就提高面积门槛，
或者只在 BLOCKED 的失败原因里提。

## D27. iframe 加载阶段不问模型：动作之后等 iframe load，白屏时只观测不决策

**决定**：
- 动作之后若有**看得见的同源 iframe 开始加载文档**，就等它的文档请求返回、再等 `load`（样式与脚本都到了），
  上限 `FRAME_LOAD_TIMEOUT_MS`（15s，从动作算起）；之后从那一刻起再给一整个 `POST_ACTION_QUIET` 窗口，
  等 iframe 里的初始化请求与渲染。看不见的 iframe（下载、上报）不等。
- 观测新增 `blankFrames`：看得见、至少占视口 1/4、却一个可操作元素都没有的同源 iframe，
  键是 `f<序号>@<timeOrigin>`。判据不看文字：没渲染完的页面常常是遮罩压着已经解析好的 DOM。
- agent 看到 `blankFrames` 时不调用模型，每 `BLANK_FRAME_POLL_MS`（500ms）重新观测一次，
  最多等 `BLANK_FRAME_WAIT_MS`（10s），开始等时记一条 info。同一个 iframe 文档等满了还是白的，
  就记一条 warn、交给模型照常决策，以后不再为它等。

**为什么**：D26 之后重跑同一个用例（`20260923-125841-ebay-d907f1`），同源 iframe 已经能读了，
但点「+ 添加产品」后 iframe 文档用了 2.2s，回来之后还要拉样式与脚本。动作之后的等待 3s 就到上限，
观测落在 iframe 白屏的时候：DOM 已经解析完、一个元素都看不见。模型拿到约 1.4k tokens 的空壳，
第 2 步就以 0.71 的概率回了 BLOCKED。白屏时模型什么都读不到，这时问它只会白花一次调用，
或者直接把运行判死。

**放弃了什么**：
- 打开 iframe 的动作最多多等 15s + 3s（计入墙钟预算）；iframe 里有加载很慢的图片时，`load` 会一直等到上限。
- 真的就是空的大 iframe（例如一块还没选内容的预览区），每个文档会白等一次 10s。
- 白屏判据只看「有没有可操作的元素」。iframe 里只有一个「加载中」的按钮时认不出来，照常交给模型。

**什么情况下该反悔**：如果报告里「等满仍是白屏」的 warn 经常出现、且那些 iframe 本来就是空的，
就把白屏判据收紧成「文档还没 load」或「没有任何可见文字」。如果打开弹窗的步骤经常等满 15s，
就把等 `load` 改成等 `domcontentloaded` + 页面安静，不再等图片。

## D28. 名字认不出是哪一个的候选，label 带上它所在的那一组

**决定**：`snapshot.js` 收完候选之后统一过一遍 label。候选的名字**弱**（空的，或者只是
placeholder）或者**撞车**（同一角色下不止一个候选叫这个名字）时，label 记成
`<名字或角色> · [header row | row <n> ·] <组文字>`。「组」是从候选往上、不含与它混淆的
候选的最大祖先：名字弱时同角色的都算混淆，撞车时同角色同名的才算。组文字超过 80 字就停在
上一层；上一层一个字都没有时截取前 80 字。名字够用且唯一的候选不变。guard 仍用 `name(e)`。
D24 里「无名勾选控件带上所在行」是这条规则的特例，一并收进来，表头行不再写
`(usually select all)`。

**为什么**：一次真跑（创建 eBay 模板）里，「库存SKU:」用组件库的 `<label>` 摆在输入框旁边、
不写 `for=`，上游的可访问名退到 placeholder，元素表里只有「请输入」。文本模型不知道
这是哪个字段，回了 `text: null`，运行终止。它和 D24 的全选框是同一个问题——名字不足以
区分候选——之前按现象各补一处，下一次换成一列「编辑」或几组「是 / 否」还会再补。

**放弃了什么**：
- 需要补的候选每个都要往上爬、每层读一次 `innerText`，大页面的观测会慢一点。
- 名字撞车与否取决于当前页面上有几个同名候选，同一个元素的 label 可能随页面变化。
  名字仍在 label 开头，`labelContains` 照常命中；写成 `^…$` 的 `labelMatches` 会失配。
- 组文字是启发式的：卡片、列表项里可能混进无关文字，最多 80 字。

**什么情况下该反悔**：如果组文字经常是一大段无关的页面文字（爬出了表单项），
就把上限从 80 字收紧，或者只在组文字里取第一段文字节点。

## D29. goal 把取值交给模型时，非个人信息的字段填测试值

**决定**：`TEXT_VALUE` 加一句：goal 把取值交给模型（「能填的都填一填」「fill in whatever
you can」）时，给**非个人信息**的字段填一个简短、合理的测试值。其余不变：个人信息绝不编造，
goal 没有交出取值时缺值仍回 `{"text": null}`，goal 给了值就用那个值。

**为什么**：D28 修好之后，同一个用例（创建 eBay 模板）的元素表已经写明「请输入 · * 库存SKU:」，
文本模型却照样回了 `text: null`：goal 里没有具体的 SKU，它就按「缺少必要信息」处理。
可是 goal 已经说了「能填的数据都填一填」，这就是把取值交给了模型。原规则防的是
编造护照号这类个人信息，SKU、备注、价格不属于这一类。用 deepseek-chat 重放了 8 组输入：
交出取值时，SKU / 备注 / 价格分别填成 `TEST-SKU-001` / `测试模板` / `19.99`；
手机号、护照号，以及 goal 没有交出取值的 SKU，仍然回 null；goal 写明 `ABC-123` 时照填。

**放弃了什么**：
- 「非个人信息」由文本模型自己判断。地址、公司名这类边界上的字段，它可能填也可能不填。
- 填进去的是模型编的值。goal 交出了取值，运行结果就不再证明「按指定的值填对了」，
  只证明流程能走通。要校验具体取值的用例，应当在 goal 里写明取值。

**什么情况下该反悔**：如果出现 goal 没有交出取值、模型却编了值的情况，或者个人信息字段被
填上了测试值，就退回原规则，改成在用例 goal 里逐项写明取值。

## D30. `<select>` / `<textarea>` 不从内容取名

**决定**：`snapshot.js` 的 `name()` 像对待 `<input>` 一样，不从 `<select>` / `<textarea>`
的子节点文字取名。这样取出空名字的下拉按 D28 处理，往上找组文字时扣掉它自己的选项文字。

**为什么**：D29 之后同一个用例填好了 SKU，下一步点开「本地产品分类: 选择」，
弹出的选择器有三列没有 label 的 `<select>`。上游的 `name()` 退到子节点文字，名字成了
全部选项拼起来的两千多字；每个选项各是一条 SELECT 候选（`名字 → 选项`），234 条加起来
约 50 万字，决策请求被 TypeSafe 以 `max_tokens_exceeded`（HTTP 400）拒绝。按可访问名的规则，
这两种元素本来就不从内容取名，它们的内容是选项与取值。

**放弃了什么**：
- 与上游 `name()` 又多了一处分叉。
- 选择器里几列都没有名字时，它们都叫 `combobox`，模型只能靠各自的选项区分。

**什么情况下该反悔**：不会退回原来的取名方式。如果「几列都叫 combobox」让模型选错列，
就给没有名字的下拉加上它在同组里的序号。

## 本文不记录什么

**尚未确定的事不在这里**——见 [architecture.md §11.3](architecture.md)。

**另有一批决定记在 [architecture.md §11.1 与 §11.2](architecture.md)**，没有在这里重复。
它们同样属于选型记录，只是更贴近具体实现：

| 决定 | 一句话 |
| --- | --- |
| `checkQuality` 的取样口径 | 只取 `executed`、只取 `full` 分布、target 还要求非空、聚合用 `min` |
| `RunStats` 归 `BudgetMeter` 独占 | 两处计数必然分叉，而分叉的表现是成本统计静默失真 |
| 砍掉 `engineOptions` | 测试引擎不该出现在用户写的 YAML 里；`createEngine` 已是注入点 |
| `passed` 是三态 | 有跳过而无失败时判 `null`，判 `true` 就是谎报覆盖 |
| 准入不做成运行的闸 | 做成闸要给 `RunStatus` 加成员，且入队时会变慢 |
| `revision` 从目录推导 | 计数器文件会漂移，目录本身不会 |
| 用例保存用乐观锁 | Windows 上文件锁难做对；静默覆盖是数据丢失 |
| 迁移只在读时发生 | 报告是物证，读进来升级再写回去等于篡改证据 |
| `modelCalls` 按实际请求数算 | 按逻辑决策算的话重试就是免费通道，最坏情况超支 3 倍 |

不在这里重复的理由是避免两处漂移——`architecture.md` 那边有完整的理由与
对应的失败模式，这里只做索引。
本文只记**已经拍板**的选型，每条都带「放弃了什么」与「什么情况下该反悔」，
这两项比「选了什么」更重要：没有前者，后来者会重新提一遍同样的问题。
