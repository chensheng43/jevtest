# 选型记录

每个决定记三件事：选了什么、为什么、**放弃了什么**。
第三条最重要——没有记录被否决的方案，后来者会重新提一遍同样的问题。

---

## D1. 用 TypeScript / Node 而不是 Python

**决定**：Node 22 + TypeScript（ESM）。

**为什么**：

1. **最难的部分零成本复用。** 参考项目里最精巧的代码是 `snapshot.js`
   （107 行原子 DOM 快照 + WeakNode 身份 + 语义守卫），它本身就是 JavaScript。
   用 Python 意味着要把这段逻辑重写一遍，而它是最容易写错的地方。
2. **没有 sync/async 分裂问题。** Playwright 在 Node 里是原生异步的。
   Python 版的同步 API 使用 greenlet，不能直接用在 asyncio 事件循环里，
   而 Web 服务天然是异步的——这会逼出一个别扭的线程池方案。
3. **白送最强调试工具。** `context.tracing.start()` 产出 `trace.zip`，
   `npx playwright show-trace` 直接打开，带时间轴与每步 DOM 快照。
   Python 版也有，但 Node 版是参考实现，生态更完整。
4. **schema 与类型同源。** 用 zod 定义一份 schema，同时得到运行时校验与 TS 类型，
   用例、报告、API 的契约不会在「校验」与「类型」之间漂移。

**放弃了什么**：Python 生态里 `pytest` 的成熟度、以及和上游仓库语言一致带来的
移植便利（改为逐行对照重写）。

**什么情况下该反悔**：如果团队完全不会 JS/TS，维护成本会盖过上述收益。

---

## D2. 用 `playwright` 库而不是 `@playwright/test` 的 runner

**决定**：只用 `playwright` 这个 npm 包，不用 `@playwright/test`。

**为什么**：

`@playwright/test` 提供了大量本项目的刚需——test runner、worker 并行、
重试、HTML 报告、JUnit 导出、trace viewer、fixtures。放弃它看起来是浪费。

但它的前提是**用例即代码**：一个用例就是一个 `.spec.ts` 文件。
而本项目的核心需求恰恰相反——**用例由 Web 表单驱动，运行时要动态生成**。
把 YAML 编译成临时 spec 文件再交给它跑，会带来一串新问题：
进程生命周期、报告回读、进度推送、用例与运行的对应关系。

我们需要自研 runner（job queue、实时进度、预算刹车、用例版本快照），
这已经超出了 `@playwright/test` 的设计意图。

**但 trace viewer 没放弃。** 用底层的 `context.tracing.start/stop` 自己产出
`trace.zip`，格式完全一致，官方的 `show-trace` 照常能用。
这是这个决定里最划算的一部分：**白拿最重要的那个工具，不接管运行模型。**

**放弃了什么**：现成的 HTML 报告与 JUnit 导出（自己写，约 200 行）、
`@playwright/test` 的 fixtures 体系、它的 `expect` 断言库。

**什么情况下该反悔**：如果用例最终变成「技术同学写代码」而非「表单填写」，
`@playwright/test` 会明显更省事。

---

## D3. 用 `node:http` 而不是 Hono / Express / Fastify

**决定**：Node 内置 `node:http` + 自写约 40 行路由。

**为什么**：

1. **依赖数量。** 本项目运行时依赖刻意控制在 3 个
   （playwright / zod / yaml）。加一个 Web 框架就是 +2。
2. **Hono 的 `writeSSE` 有已知问题**——连接静默断开时可能挂起且
   `onAbort` 不触发（[#1902](https://github.com/honojs/hono/issues/1902)、
   [#3540](https://github.com/honojs/hono/issues/3540)）。
3. **我们本来就不需要 SSE**（见 D4），而 SSE 正是 Hono 相对标准库最大的优势。

**放弃了什么**：成熟的路由、中间件、body 解析、类型化上下文。
实际要手写的是：路径模式匹配（十几行）、请求体流式限长（十几行）、
静态文件服务（十几行）。总量可控。

**什么情况下该反悔**：端点数量增长到几十个、或需要 SSE/WebSocket。
反悔成本低——路由集中在 `web/api.ts`，换框架只改两个文件。

---

## D4. 进度用轮询而不是 SSE

**决定**：前端 500ms 轮询 `GET /api/runs/:id/events?since=<seq>`。

**为什么**：

- 进度事件是**服务端单向**推送，SSE 的双向能力用不上；
- 一次运行约 10~20 步，几步每秒，500ms 轮询完全够用；
- SSE 会引入连接生命周期、心跳保活、断线重连、代理缓冲等一串失败面；
- 事件模型本身是 SSE 兼容的（`seq` 天然对应 `Last-Event-ID`），
  真要换，改动集中在一个端点和 `web/events.ts`。

**放弃了什么**：更低的延迟与更少的请求数。在本项目的规模下不值得。

**什么情况下该反悔**：如果实测发现长运行（>5 分钟）时轮询体验差，
或者步数密度远超预期。

---

## D5. 用例格式用 YAML，Web 表单是它的图形编辑器

**决定**：`case.yaml` 落盘为**唯一事实来源**；表单只是编辑它的界面。

**为什么**：

两套模型（表单一套、文件一套）迟早会漂移——表单里能设的字段文件里没有，
或者反过来。漂移之后没人知道哪边是真的。

单一事实来源解决了这个问题，并带来两个额外好处：
**用例可以进 Git**（有 diff、有 review、能回滚），
**非技术同学也能用表单编辑同一份文件**。

保证不漂移的机制：`tests/yaml-roundtrip.test.ts` 锁「YAML ↔ 对象」逐字节往返，
`tests/frontend.test.ts` 锁「对象 → 表单草稿 → 对象」语义不变。

**放弃了什么**：纯数据库存储的灵活性（查询、并发编辑、权限）。
本项目是单机工具，文件足够。

**什么情况下该反悔**：如果变成多人协作的集中式平台。

## D6. 断言分三层

**决定**：`final`（最终页面）/ `trajectory`（动作轨迹）/ `quality`（质量与成本）。

**为什么**：

上游只有一个**硬编码给 Google Flights** 的 `verify()`。要泛化它，
先得想清楚断言到底在回答哪些不同的问题——它们混在一起会给出误导性的报告。

| 层 | 回答的问题 | 失败的典型含义 |
| --- | --- | --- |
| `final` | 最终页面对不对？ | 功能有缺陷，或断言写太严 |
| `trajectory` | 过程走对了吗？碰了不该碰的吗？ | 它绕路了，或护栏失效 |
| `quality` | 跑得稳不稳、贵不贵？ | 用例不稳，或性能回归 |

分开的实用价值：一次失败时能立刻定位到**是哪一类问题**。
「页面是对的但它绕了 40 步」和「页面根本不对」需要完全不同的处理。

**放弃了什么**：一层 `assert` 列表的简洁性。

---

## D7. `trajectory` 断言按 label 而非内部 id

**决定**：轨迹断言用 `labelContains` / `role` / `kind` 匹配，
不用内部的 `e7` 这种 id。

**为什么**：内部的 `choice` 是 code-owned 节点身份，**只在单次观测内有效**。
节点被替换会拿到新身份，导航会重置整个缓存。
因此它**跨运行完全不可比**——用 `mustUse: ["e7"]` 断言毫无意义。

而轨迹记录里存了人类可读的动作标签（上游 `agent.py:121-141`），
它才是稳定的、有语义的匹配依据。

**放弃了什么**：精确匹配某一次特定点击的能力。
但那个能力本身就是幻觉——下一次运行它就不是那个 id 了。

---

## D8. `status` 与 `passed` 是两个类型，且都保留

**决定**：`status: RunStatus`（循环如何结束）与 `passed: boolean | null`
（断言判决）相互独立。

**为什么**：上游 README 里有一句核心信条——
**A `DONE` choice is not proof of success.** 它用独立的 `verify()` 检验结果，
而不是相信模型的自我判断。

把这条纪律固化到类型层面，写错编译器就会拦下。同时 `passed` 允许为 `null`，
表示「未能求值」（例如第一步之前就超预算了，没有最终页面可断言）——
把它当成 `false` 是另一种谎报。

**放弃了什么**：一个布尔字段的简洁性。

---

## D9. 结果有三种状态：passed / failed / skipped

**决定**：`CheckResult` 带 `skipped` 字段，而不是布尔值。

**为什么**：

TypeSafe 给出真实的概率分布，但通用 LLM 通常只回一个选择，
合成出来是 one-hot 1.0。此时 `quality.minTargetProbability: 0.3`
**永远通过**——因为「被选中项的概率」恒等于 1.0。

这是一个**假通过**，比失败更危险：它让人以为测过了，而实际没有覆盖。

所以引擎通过 `capabilities.probabilities` 声明自己给的是
`full` 还是 `degenerate` 分布；断言层看到 `degenerate` 时，
概率类检查返回 `skipped`，报告显示「跳过」。

**放弃了什么**：一个布尔字段的简洁性（同上）。

**推论**：报告里「跳过」的视觉呈现必须与「通过」明显不同。

---

## D10. 只读模式在动作空间构造阶段实现

**决定**：`mode: readonly` 时，变更型操作在 `buildActionSpace` 里就被剔除，
不进入候选集。而不是「模型选了之后我们拒绝」。

**为什么**：

| | 构造阶段剔除 | 事后过滤 |
| --- | --- | --- |
| 模型能否选中 | **物理上不能** | 能选中，被拒绝 |
| 拒绝逻辑写漏的风险 | 不存在 | 每加一个操作都要记得加判断 |
| 报告能说什么 | 「本运行不可能发生变更」 | 「我们相信它没发生」 |

这复用了上游最有价值的机制：**有限选择空间即安全边界**。
上游的模型从来只能从观测到的元素里挑一个索引，
这个约束本身就消灭了一整类风险（伪造选择器、注入脚本、越界点击）。
只读模式是同一思路的延伸。

`core/guard.ts` 的 `auditTrajectory` 仍会事后核对一遍——
**「物理上不可能」和「报告需要证据」是两回事。**

**放弃了什么**：没有。这个实现方式严格优于事后过滤。

---

## D11. 每个用例一个 `BrowserContext`，删掉全局锁

**决定**：一个 Chromium，每用例一个 context；不做全局串行化。

**为什么**：

上游用一把全局 `LOCK` 序列化所有浏览器步进
（`demo.py:111-112`），因为所有标签页共享用户已有的 Chrome profile。

换到 Playwright 后：

| | 上游 | 本项目 |
| --- | --- | --- |
| profile | 共享 | 每 context 独立 |
| cookie/localStorage | 互相污染 | 隔离 |
| 并行 | 不可能 | 天然支持 |
| 登录态 | 手动维护 | `storageState` 复用 |
| 单实例成本 | 新建标签页 | ~50ms、80~150MB |

**锁必须删掉**——它存在只是因为当时只有一个共享标签页，
在隔离是天然的情况下，锁只会杀掉并发。

**放弃了什么**：复用用户 Chrome 已有的登录态（改为 `storageState` 机制），
以及直接观察用户浏览器窗口的便利（调试时略麻烦，靠 trace viewer 补）。

**代价**：Playwright 自带的 Chromium 不是真实 Chrome，且带
`--enable-automation` 特征。内部 staging 无所谓，测三方站点时要留意。

## D12. 引擎可插拔，校验在引擎之外

**决定**：定义供应商无关的 `DecisionRequest` / `DecisionResult` IR；
`validateChoice` 住在 `core/policy.ts` 而不是引擎里。

**为什么**：

绑死 TypeSafe 会让项目受制于单一供应商的可用性与定价。
但「可插拔」很容易做成表面功夫——如果每个引擎各自校验自己的输出，
换一个引擎就等于换一套安全保证。

把校验放在 `core/` 意味着：**引擎无法产出越界的选择**。
即使某个实现有 bug 返回了不存在的 id，也会被挡在执行之前。

同时 `capabilities` 让引擎如实声明自己的能力（是否支持文本生成、
概率分布是 full 还是 degenerate），断言层据此决定哪些检查可求值。

**放弃了什么**：引擎可以自由优化输出格式的便利（必须装进 IR）。

**代价**：IR 是为了同时容纳「TypeSafe 的多问题结构化输出」和
「通用 LLM 的 tool use」设计的，对两者都不是最优解。

---

## D13. 报告自包含（内嵌用例快照与 digest）

**决定**：`runs/<runId>/` 里存一份产生本次运行的 `case.yaml` 快照，
报告里记录 `caseRevision` 与 `caseDigest`。

**为什么**：

用例会被修改。如果报告只记录 `caseId`，一周后翻出一份失败报告，
你不知道当时跑的是哪个版本的用例——那个失败可能已经被修好了，
也可能被你的修改掩盖了。

自包含之后，任何一份报告都能精确回到产生它的用例版本。

这是上游 `measurement.json` 里 `source_hashes` 的正规化版本——
它记录了源码的 hash，本项目把同样的思路用在用例上。

**放弃了什么**：磁盘占用（每个 run 多一份 YAML，微不足道）。

---

## D14. 内置护栏只增不减

**决定**：用例只能往护栏里**追加**规则；移除内置规则需要显式设置
`allowDefaultOverride: true`，且报告应打红色横幅（**尚未落地**：报告目前不记录这件事，见 [limitations.md §9](limitations.md)）。

**为什么**：

安全网最常见的失效方式不是「没配」，而是「被悄悄关掉」——
某次调试时注释掉一行，然后忘了加回来。

让它**默认安全，放弃安全需要明说并留痕**，比相信人的自觉可靠。

**放弃了什么**：纯粹配置的灵活性。这个交换是值得的。

---

## D15. 用 `node:test` 而不是 vitest

**决定**：Node 内置测试运行器。

**为什么**：`node:test` 在 Node 22 上已经足够（支持并发、子测试、mock、
快照）。引入 vitest 意味着 +1 个开发依赖和一整棵依赖树，
而本项目需要的能力它并不比内置的多。

**放弃了什么**：更丰富的断言 API、更好的 watch 模式、更成熟的生态集成
（如浏览器模式的测试）。

**什么情况下该反悔**：如果需要组件测试或更复杂的 mock 场景。

---

## D16. CLI 走进程内调用，不经过自己的 HTTP 服务

**决定**：`jevtest run` / `validate` / `import` 直接调用模块（`cli.ts` 的 `createWiring`），
`doctor` 调 `web/api.ts` 的 `handle()` 但**不经网络**。

**为什么**：为了跑一个用例去绑端口、生成一次性令牌、启动一个「浏览器都还没起」的 HTTP 服务、
再让它把请求转发一次，只增加失败面；CI 里并行跑多个 jevtest 还会撞端口（或需要各自分配端口）。
而 `doctor` 要检查的是配置与依赖，不是 TCP——它走的是**同一个 handler**，只是不经过 socket。

**放弃了什么**：「CLI 就是 HTTP API 的一个客户端」这种整齐。前端与 CLI 在
**语义与业务逻辑上**共用同一套（同一份路由与模块），在传输层不共用。

**什么情况下该反悔**：若要支持「CLI 连远程 jevtest 服务」（多机场景），就必须真的走 HTTP——
那时 `createWiring` 与一个纯 HTTP 客户端会是两条并列的通路，而不是二选一。

---

## D17. 只读模式剔除的角色从 6 个扩到 10 个

**决定**：`READONLY_BLOCKED_CLICK_ROLES` 增加 `menuitemradio`、`menuitemcheckbox`、`option`、`gridcell`。

**为什么**：最初那 6 个（`docs/case-format.md` §mode 里的原始清单）是照搬参考项目的概念定的，
漏了 ARIA 的选项与菜单选项，以及日历/表格的单元格。它们的点击**同样会改变被提交的值**，
与勾选框同类。少列一个，只读用例就能悄悄改掉页面状态——而报告里那句
「本运行不可能发生变更」就变成了假话。

**放弃了什么**：只读用例能点到的控件变得更少（例如点不开日历选择日期）。这是刻意的取舍：
只读的承诺要么是真的，要么就别写。

**代价与防漂移**：清单现在同时写在代码与两份文档里，因此加了一条测试，
从**代码常量**出发逐条验证、并比对文档里的清单——两处事实来源靠测试钉住，靠人同步必然漂移。

---

## D18. 前端引入 Bootstrap，经 `/vendor/*` 静态提供

**决定**：`bootstrap`（`^5.3.8`）进 `dependencies`，前端从 `/vendor/bootstrap/dist/css/*.min.css`
引它的样式表。`VENDOR_EXTENSIONS` 因此从 `.js` / `.map` / `.json` 扩到含 `.css`。

**为什么**：

前端原先是一份手写 CSS（约 60 行），后来要支撑的界面（用例列表、表单编辑器、
运行结果页、断言逐条明细、事件流）已经不是「加几十行」的规模。手写下去的真实代价
不是行数，而是**一致性**：间距、层级、focus 态、深浅色各自为政，每加一个视图都要
重新决定一遍。Bootstrap 把这些决定收敛成一套既有约定。

经 `/vendor/*` 而非 CDN：这个服务只监听回环、且刻意不依赖外网
（`docs/architecture.md` §8），从 CDN 引样式会让「离线可用」这条作废。

**放弃了什么**：

- 「运行时依赖只有 3 个」这条硬约束（现在 4 个）。它是**可以被放弃的**——那 3 个是
  出于「每个依赖都是一处长期维护面」的判断，而不是数字本身有魔力。
- 前端的完全自主样式（继承 Bootstrap 的设计语言，包括它的间距刻度与栅格）。

**代价**：

- `/vendor/*` 从「只为 zod 存在」变成「前端资产通道」。它是全项目**唯一**的动态文件
  服务路径，也就是唯一的目录穿越风险点——放行 `.css` 不引入新的风险面
  （静态读取，扩展名只决定「能不能读」，不存在按内容执行的路径，且 `.css` 不像
  `.html` 那样会被注入令牌），但这条路由的总风险随它服务的东西变多而变多
  （见 `docs/security.md` §5）。
- 前端不再零依赖构建之外的约束——但只要不引入打包器，这条底线还在。

**什么情况下该反悔**：若前端开始需要 JS 组件（`bootstrap.js` 的 dropdown/modal 之类），
就该重新权衡——那会把 `/vendor` 从「读几个静态文件」变成「运行第三方脚本」，
与 `docs/security.md` 的信任边界直接相关。届时更稳的做法是把需要的 CSS/JS
**vendor 进仓库**（进 `src/web/public/`），而不是让 `/vendor` 指向 `node_modules`。

## D19. 界面按「此刻要判断什么」分档，编辑器以草稿为唯一事实来源

**决定**：三条一起。

1. **编辑用例**分成四档（基本 / 断言 / 预算与护栏 / 保存内容）。
2. **断言不再按 schema 的三层平铺**，改成**配方行**——一行一句人话
   （「最终页面包含文本」「结束方式必须是」……），每行落到 schema 的一处。
   配方覆盖不到的构造不在界面上消失，而是收进同一档的「其他（配方之外的断言字段）」，
   非空时默认展开。
3. **结果页**判决卡常驻，下面按 断言 / 轨迹 / 事件日志 分档；运行中默认落在
   事件日志，结束后默认落在断言（用户自己点过之后就不再替他切）。

配套的三条实现约定：标签页与折叠**手写 / 用原生 `<details>`**（不引 `bootstrap.js`，
理由见 D18）；**编辑器的草稿是唯一事实来源**，`formToDefinition(draft)` 是纯函数，
控件一律在 input 时写回草稿；构建子节点列表统一用 `setChildren(node, [...])`。

**为什么**：原先的编辑器把 schema 平铺成一页，既难用、手动配置也太繁琐。当时一页 38 个控件，**其中 13 个
只有 placeholder 没有 label**——填进第一个字符之后就再也看不出那一格是什么；
断言三层里的 12 个 text-match 输入框还都是 `<input>`，而 HTML 规范规定
`<input>` 的值里不能有换行，于是「每行一条」这句 placeholder 是在承诺一件
输入框做不到的事。schema 里约 53 个叶子槽位一个都不能少，所以出路不是删字段，
是分层：**默认只露出常用路径，其余可发现但不挡路**。

字段与交互的映射按「用户此刻要做的判断」排，而不是按 schema 的结构排。
配方那句话直接取自 `docs/writing-cases.md §3`——界面与文档用同一套词汇。

**放弃了什么**：

- **一页看到所有字段。** 要改 `minTargetProbability` 得先切到断言档、
  再展开「其他」。这是刻意的：那些字段不常用，而常用路径值得一条干净的路。
- **第 4 档显示 JSON 而不是 YAML。** 真正的规范化 YAML 只有服务端
  `schema/yaml.ts` 会写；前端自己实现一份必然与它漂移，那就是在界面上撒谎。
  要看真 YAML，用同档的「导出已保存的 YAML」（走 `GET /api/cases/:id/export`）。
- **标签页与折叠没有过渡动画**（Bootstrap 的 collapse/tab 才有）。手写的四十行
  换掉一次 `/vendor` 信任边界的重估，值。

**代价与防漂移**：`tabs()` / `setChildren()` / `RECIPES` / `RAW_FIELDS` 几张表让前端代码明显变长。
真正的风险是**配方这层视图会不会把用例改坏**——载入一个用例、界面重画一遍、再保存，
中间丢一条断言是不会报错的。所以 `tests/frontend.test.ts` 把 `app.js` 里标了 `#region 纯函数`
的两段抠出来（`new Function`，不引 jsdom），跑三件事：种子用例往返语义不变、**每个配方与
每一处原始字段都落得下去**、以及空 `statusIn` 原样活着。往那两段里加代码时
不许引用 DOM——那是这个项目里唯一能不引 DOM 测试环境就测到前端逻辑的口子。

**什么情况下该反悔**：若配方这层视图开始需要「一条断言里混合配方内外的字段」，
说明它已经从视图变成了数据模型，那时该重新设计的是数据形状而不是加特例；
若要给界面加 modal / tooltip 之类的 JS 组件，先按 D18 重估 `/vendor`。

## 本文不记录什么

**尚未确定的事不在这里**——见 [architecture.md §11.3](architecture.md)。

**另有一批决定记在 [architecture.md §11.1 与 §11.2](architecture.md)**，没有在这里重复。
它们同样属于选型记录，只是更贴近具体实现：

| 决定 | 一句话 |
| --- | --- |
| `checkQuality` 的取样口径 | 只取 `executed`、只取 `full` 分布、target 还要求非空、聚合用 `min` |
| `RunStats` 归 `BudgetMeter` 独占 | 两处计数必然分叉，而分叉的表现是成本统计静默失真 |
| 砍掉 `engineOptions` | 测试引擎不该出现在用户写的 YAML 里；`createEngine` 已是注入点 |
| `passed` 是三态 | 有跳过而无失败时判 `null`，判 `true` 就是谎报覆盖 |
| 准入不做成运行的闸 | 做成闸要给 `RunStatus` 加成员，且入队时会变慢 |
| `revision` 从目录推导 | 计数器文件会漂移，目录本身不会 |
| 用例保存用乐观锁 | Windows 上文件锁难做对；静默覆盖是数据丢失 |
| 迁移只在读时发生 | 报告是物证，读进来升级再写回去等于篡改证据 |
| `modelCalls` 按实际请求数算 | 按逻辑决策算的话重试就是免费通道，最坏情况超支 3 倍 |

不在这里重复的理由是避免两处漂移——`architecture.md` 那边有完整的理由与
对应的失败模式，这里只做索引。
本文只记**已经拍板**的选型，每条都带「放弃了什么」与「什么情况下该反悔」，
这两项比「选了什么」更重要：没有前者，后来者会重新提一遍同样的问题。
